# マニュアルに期待すること

当日マニュアルから抜き出したい項目の一覧。項目ごとに「なぜ要るか」と「書いていないときにどう調べるか」を持つ。

マニュアルを読んだら、全項目を次の 3 つに分ける。

- **記載あり**: マニュアルの値を仮説として使い、サーバで確かめる
- **記載なし・サーバで調べられる**: 下の「無いときの調べ方」を実行する
- **記載なし・サーバでは分からない**: ルールや運営の都合に関わる項目。推測で埋めずに、ユーザーに確認するか、安全側の前提を置いて明記する

例の列は ISUCON9 予選 (isucari) での値。

## A. 環境

| # | 項目 | なぜ要るか | ISUCON9 予選の例 | 無いときの調べ方 |
|---|---|---|---|---|
| A1 | サーバ台数と、使ってよい上限 | Makefile のホスト変数。上限超えは失格になりうる | 最大 3 台 | 分からない。ユーザーに確認 |
| A2 | 各サーバのスペック | 役割分担 (DB を分けるか) の判断 | ecs.sn1ne.large | `nproc; free -h; df -h /` |
| A3 | SSH のユーザーと認証方法 | `~/.ssh/config` の `User` と鍵 | root、キーペア | `ssh -v` で試す。root / isucon / ubuntu の順。sshd の `AuthorizedKeysFile` も見る |
| A4 | 触ってはいけないユーザー・鍵・プロセス | 消すと失格や追試不能 | `isucon_admin` と公開鍵 | 分からない。`getent passwd` と authorized_keys を一覧してユーザーに見せ、消さない前提で進める |
| A5 | 外部リソースの利用可否 | 外部のサーバやサービスを使ってよいか | 外部のメトリクス計測のみ可、スコアに効くものは不可 | 分からない。ユーザーに確認。確認できるまで外部のものは使わない |

## B. アプリとミドルウェア

| # | 項目 | なぜ要るか | ISUCON9 予選の例 | 無いときの調べ方 |
|---|---|---|---|---|
| B1 | 参照実装のサービス名と初期言語 | `SERVICE`。調査の grep パターン | `isucari.golang.service`、初期は Go | `systemctl list-units --type=service --state=running`。アプリのポートから逆引き: `sudo ss -ltnp` の pid → `systemctl status <pid>` |
| B2 | 言語の切り替え手順 | 切り替えで nginx 等の設定も変わるか | PHP だけ nginx の conf も差し替え | `/etc/nginx/sites-available/` に言語別の conf が無いか見る |
| B3 | アプリのディレクトリとビルド方法 | `EXEC` (`APP_DIR` / `BIN` / `WEBAPP` はここから決まる) | `/home/isucon/isucari/webapp/go/isucari` | `systemctl cat <service>` の `ExecStart`。そのディレクトリに go.mod があるか |
| B4 | 環境変数・接続先の設定 | DB を分けるときに直す場所 | `/home/isucon/env.sh` | `systemctl cat` の `EnvironmentFile` と `Environment=` |
| B5 | Web サーバと DB の種類・バージョン | 設定ファイルの置き場所と使えるオプション | nginx、MySQL | `nginx -v`、`mysql --version`。MariaDB なら conf は `mariadb.conf.d/` |
| B6 | 公開ポート、TLS、ホスト名 | smoke の URL。ブラウザ確認の方法 | 80 / 443、証明書は `isucon9.catatsuy.org` | `sudo ss -ltnp`。nginx の `listen` と `server_name`。証明書は `openssl x509 -noout -subject -ext subjectAltName -in <cert>` |
| B7 | DB の初期化・リカバリ方法 | 壊したときに戻す | `webapp/init.sh` | `find ~ -name 'init*.sh'`、`webapp/sql/`。`POST /initialize` のハンドラが何をしているか読む |
| B8 | 外部サービスへの依存 | 手元の動作確認に必要。遅さの原因になりうる | payment / shipment サービス | コードで外部 URL や HTTP クライアントを grep。`docs/` を読む |

## C. ベンチとルール

| # | 項目 | なぜ要るか | ISUCON9 予選の例 | 無いときの調べ方 |
|---|---|---|---|---|
| C1 | ベンチの実行方法 | 改善の効果を測る手段 | ポータルから Enqueue | サーバや手元にベンチマーカーが無いか探す (`sudo find /home /opt /usr/local /root -iname '*bench*' -type f -perm -u+x 2>/dev/null`。`/` 全体だとカーネルのサンプルが大量に出る)。無ければユーザーに確認 |
| C2 | ベンチの流れと時間制限 | 最初に守るべき性能要件 | `/initialize` は 20 秒、各レスポンスは 10 秒以内 | 分からない。ユーザーに確認。確認できるまでは「初期実装より遅くしない」を前提にする |
| C3 | スコアの計算方法と減点 | どこを速くすると効くか | 取引が完了した商品の価格合計 − 減点 | 分からない。ユーザーに確認 |
| C4 | 失格条件 | 絶対に踏んではいけない線 | critical error 1 回、ステータス誤り 10 回 | 分からない。ユーザーに確認 |
| C5 | 仕様として変えてはいけない挙動 | キャッシュや省略をしてよい範囲 | 一覧の件数は初期実装と同じ、更新は即時反映 | 分からない。確認できるまで、レスポンスの中身は初期実装と完全に同じにする |
| C6 | 永続化と追試の条件 | インメモリ化してよいか、再起動試験 | 再起動後もデータが残ること、平文パスワード禁止 | 分からない。確認できるまで、全データを DB に永続化する前提にする |
| C7 | 特別な応答の要件 | 空だと失格になる項目など | `/initialize` の `language` と `campaign` | `/initialize` のハンドラを読み、返している JSON を確認する |
| C8 | 終了時・終了後の作業 | 最終チェックとインスタンスの扱い | 追試まで止めない | 分からない。ユーザーに確認 |

## 使い方の注意

- **「分からない」の項目を推測で埋めない。** 特に A1, A4, A5, C2〜C6 は、間違えると失格につながる。
- **練習環境はマニュアルと違うことがある。** 過去問の再現環境では、A3, B1, B6, C1 がよくずれる。記載ありの項目も、サーバで確かめてから使う。
- **結果は notes に残す。** 「マニュアル (本番)」と「サーバの実物」の 2 列で書き、ずれた項目を残す。
