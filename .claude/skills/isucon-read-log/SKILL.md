# ベンチの結果を読む

`make measure` は、ベンチ 1 回分を `log/<bench>/` に残す。`<bench>` は `make measure` を叩いた日時 (`20261006-123712` の形) で、ポータルの履歴の時刻と突き合わせられる。

| ファイル | 中身 |
|---|---|
| `log/<bench>/alp.tsv` | エンドポイントごとの集計。列は 回数、2xx、4xx、5xx、method、uri、合計、平均、p90、最大 (秒)。合計の大きい順 |
| `log/<bench>/slow.tsv` | クエリの形ごとの集計。列は クエリの形、回数、合計、平均、Rows_examined の合計。合計の大きい順に 50 件 |
| `log/<bench>/pprof.txt` | CPU プロファイル。top (flat)、top (cum)、`main.` の関数だけの cum 順、直前のベンチとの diff、`main.` の重い関数のソース |
| `log/<bench>/commit.txt` | 計測したときのコミット |
| `log/<bench>/cpu.pprof` | 合算した CPU プロファイル (バイナリ)。`pprof.txt` に無い見方をしたいときだけ `go tool pprof -top -focus=<関数> ...` などで開く |

## 手順

1. **どのベンチを読むか決める。** 指定が無ければ、`ls -d log/*/ | sort | tail -2` の新しい方が今回、古い方が直前。`pprof.txt` は無いことがある (アプリが pprof の口を開けていない、または終了前に外した)
2. **何を変えたかを見る。** `git log --oneline <直前のコミット>..<今回のコミット>` で見る。スコアは log に無いので、必要ならユーザーに聞く (ポータルの履歴にある)
3. **alp を読む。**
   - 合計の大きい行から見る。合計は回数 × 平均なので、回数が多いのか、1 回が遅いのかを分けて書く
   - 5xx がある行は、速さより先に落ちている原因を見る (`make log`)
   - 回数が少なくて ID やユーザー名の入った uri が並んでいたら、`tools/alp.yaml` の `matching_groups` のまとめ忘れ。ユーザーに伝える
   - 直前との差は次で出す。出力は「差、今回の合計、method と uri」で、マイナスなら速くなった。`matching_groups` を変えた直後は比べられない
     ```bash
     awk -F'\t' 'NR==FNR {p[$5" "$6]=$7; next} {k=$5" "$6; printf "%+8.2f\t%8.2f\t%s\n", $7-p[k], $7, k}' log/<直前>/alp.tsv log/<今回>/alp.tsv | sort -n
     ```
4. **slow を読む。**
   - 合計の大きいクエリから見る
   - Rows_examined の合計を回数で割った値 (1 回で読んだ行数) が大きいクエリは、index が効いていない疑いがある。テーブル定義 (`webapp/sql/` など) と見比べる
   - 1 回は軽いのに回数が多いクエリは、N+1 の疑いがある。どのハンドラから呼んでいるかをコードで探す
5. **pprof.txt を読む。**
   - 先頭の `requests` は alp の回数の合計。CPU 時間の差は、必ずこの数と一緒に読む。リクエスト数が増えれば、ほとんどの関数の CPU 時間が増える
   - `Duration` はベンチの長さではない (deploy / prep から measure までの時間)。負荷のない時間はサンプルが 0 なので、中身には混ざらない
   - 「main. の関数 (cum)」の節で、どのハンドラが CPU を使っているかを見る。top (cum) は net/http や echo、DB ドライバが上を占めるので、アプリの関数はこの節で見る。alp の上位のエンドポイントと対応させる
   - top (flat) の上位がランタイム (`memmove` `mallocgc` `scanobject` `Syscall` など) ばかりでも、それ自体は直せない。cum で、どのハンドラから来ているかをたどる
   - diff はマイナスが減った関数。今回の変更が狙いどおり効いたかを確かめる
   - list の行ごとの時間で、重い行を `ファイル:行` で示す。ソースは手元のリポジトリから読んでいるので、HEAD が `commit.txt` と違えば行がずれている。そのときは `git show <commit>:<ファイル>` で見る
6. **3 つを突き合わせる。** alp で重いエンドポイント → pprof.txt のハンドラ → その中で発行している slow のクエリ → コードの行、の順につなげる
   - CPU プロファイルには、DB やロック、外部サービスの待ち時間は出ない。alp で遅いのに pprof.txt で CPU を使っていないハンドラは、待ちが原因。slow のクエリやコードの外部呼び出しを見る
7. **ユーザーに返す。**
   - 最初に、直前のベンチから何が変わったか (今回の変更は効いたか) を一言で書く
   - 次に直す候補を、効きそうな順に 3〜5 個挙げる。各候補に、場所 (エンドポイント、クエリ、`ファイル:行`)、根拠 (log の数字)、直し方を書く
   - コードは、頼まれるまで直さない
